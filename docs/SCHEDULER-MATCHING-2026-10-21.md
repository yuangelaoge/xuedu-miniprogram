# 排班匹配中的备选数量优化

发布更新（2026-10-21）：d2b11ce 已合入私有 main 并部署既有 xueduTrial；未上传前端、执行 SQL 或生成线上排班。以下“未推送、部署”为开发交付阶段状态，最新证据见 [部署记录](DEPLOYMENT-2026-10-21-MATCHING.md)。

## 范围与规则

基于本地 main `0d48a79`（1.3.3 发布记录），在独立分支 `codex/schedule-candidate-matching` 开发。只调整共享 scheduler 与相应测试、文档；无新接口、前端页面或数据库结构变更。

用户明确：不听本人班级是硬限制，包含本人的合班及每一个备选也必须排除；上周听过的班级本周优先避开，仍是可放宽的偏好，不按课程名称禁排。

依次优化：

1. 保持现有最大教学班组匹配数量及行政班覆盖处理。
2. 指定优先年级。
3. 上周未被听班级。
4. 上周未听课成员。
5. 非第 1 节开始的推荐课程。
6. 拥有至少 2 门有效候选的已安排成员数量。
7. 在以上目标相同时，最大化有效候选课程总数。

沿用精确班级 ID 集合组成的教学班组，交叉合班仍拒绝生成；不跨班或跨专业拼接候选。所有课程必须符合本人班级排除、目标学期周次、整段无课时间、报名与启用状态。一个任务多个同班候选，任选一门提交一次；每人每周一次、已完成任务冻结、人工确认规则保持。

同一目标周中，相同班级集合、课程名、教师、教室、星期及起止节次只算一次；不同 ID 的重复导入不会增加备选。保留第一条的 ID/原快照，不修改源课表；人数、性质标签、有效周列表差异不生成额外选择。同名但不同教师或时段保留。同一 ID 若对应不同上述课程内容则拒绝生成，提示核对。既有任务不回写，也不删除其候选。

## 为什么不会挤占高优先级

保留单位容量的最小费用最大流图：源点 → 班组 → 成员 → 汇点，直到没有增广路。源点至班组的费用是：

`[最大班组规模−本组规模, 非优先年级, 上周已听班, 0, 0, 0, 0]`

班组至成员的费用是：

`[0, 0, 0, 上周已听成员, 推荐课程为早八, −是否至少2门, −候选数]`

逐个分量按词典序比较，不合并成一个巨大整数。固定流量下首项总和为常数减行政班覆盖数。对于不重叠班组，增广路保留原先已覆盖班组并新增一个班组，因此最大匹配不损害行政班最大覆盖。后续各分量分别对应上述偏好，低优先级累加再多也不能抵消高优先级的一点差异。

反向边逐项取负，Bellman–Ford 找词典序最短增广路；词典序对加法保持顺序，原有逐次最短增广正确性继续成立。起始残量图无环，最短增广保持无负费用环，最终得到固定最大流量下的词典序最小费用。没有在已排好结果上逐人贪心补课，也没有截断候选列表。

每个分量来自整数计数。初始化检查 `(节点数−1)×max(最大班组规模, 目标周去重课程数, 1)` 为安全整数；每次距离加法再用 `Number.isSafeInteger` 检查所有分量，超界拒绝，避免隐式精度损失。服务端既有单任务最多 100 门候选上限不变。

## 本地实测（纯合成数据）

基线算法直接取 `0d48a79:miniprogram/domain/scheduler.ts`，同一输入、同一 revision 对比：

| 场景 | 覆盖任务数，前→后 | 至少2门人数，前→后 | 候选总数，前→后 |
| --- | --- | --- | --- |
| 问答两人 A/B 反例 | 2→2 | 0→2 | 2→6 |
| 40人、40班组、400门课程；固定 seed=40、revision=0 | 40→40 | 26→40 | 81→146 |
| 另一组原已充足的40人模拟 | 40→40 | 40→40 | 383→383 |

两人反例结果为甲听 B、乙听 A，各有 3 门，而原来各 1 门。另一个构造案例确认两人各 2 门（共 4 门）优先于一人 1 门、另一人 8 门（共 9 门）；两人都至少 2 门后才比较总数。

40人固定 seed 模拟重复 20 次，本地纯计算中位耗时从约 5.39ms 增至 24.54ms，新算法最大约 30.22ms。向量比较有额外计算成本；这不是云端时延测量，也不包含网络或数据库。40人 fixture 保存在 `tests/helpers/scheduler-matching.ts`；运行结果留在本地忽略目录 `artifacts/scheduler-matching/benchmark.json`。

不承诺每个人都有两门：课表、本人班级、无课时间或更高优先级可能使一门成为最优可行结果。纯合成收益不能代表真实成员收益；本轮未读取真实排班或成员资料。
