## 目标和边界

沿用 AppID、环境 `xuedu-trial-d2gs2dpnla9206eb3`、函数 `xueduTrial` 及现有私有照片桶。名字中的 trial 是历史标识，V2 业务模式统一为 cloud，不因此建立新环境或购买套餐。迁移输入中的 `document.stage` 仍是旧协议的 `trial`。

本次切换只迁入全部管理员和这些管理员引用的班级。包括停用管理员；姓名、学号、原成员 ID、班级 ID、微信绑定、角色、启停状态及其他成员资料完整保留。共享班级只保留一份完整资料。微信标识迁入独立 bindings 资源，不在成员查询中暴露。原学期、课表和记录不迁入新业务表；管理员以后从管理工作台建立新学期。

没有有效管理员、管理员缺少绑定班级、管理员身份/学号重复、输入是把微信标识替换为 self 的客户端快照，均停止。发现旧 `cleaning`、`resetAll` 或 `businessClear` 任务也停止；必须先通过旧版本受控维护流程完成该任务，不能手改字段解冻、跳过照片或自动升级。

## 离线材料

`scripts/v2-cutover.mjs` 不加载云 SDK、凭据或网络接口。输入必须是受控的服务端完整导出，不能使用按角色过滤的 `snapshot`：

```json
{
  "environmentId": "xuedu-trial-d2gs2dpnla9206eb3",
  "functionName": "xueduTrial",
  "revision": 12,
  "document": {
    "stage": "trial",
    "epoch": "旧轮次",
    "version": 9,
    "state": "完整旧 AppState 对象；此字符串仅说明格式",
    "receipts": [],
    "files": []
  }
}
```

`revision` 是 PG 的 CAS revision，不能用 `document.version` 代替。只导出工作区业务数据，不导出 API Key、数据库密码、AppSecret 或平台登录信息。

在仓库外已经存在的受控父目录中创建一个全新的材料目录：

```sh
node scripts/v2-cutover.mjs plan /受控目录/source.json /受控目录/cutover-materials 3000
```

最后一个参数是经独立核实的**实际函数执行上限（毫秒）**，示例 3000 不是固定配置要求。范围 1000–900000，必须与将部署的 V2 服务端配置相同；排空和租约据此推导，平台配置改变时应重新核对。脚本生成随机新轮次，不能沿用旧轮次。

目录权限 0700，以下文件权限 0600，不覆盖已有目录或文件，拒绝向任何 Git 工作树写材料：

- `legacy-recovery.json`：原输入字节的副本，用于独立恢复和核对。保留旧业务资料，属于敏感材料。
- `retention-plan.json`：V2 workspace 和 members/classes/bindings 实体。workspace 保持维护状态；没有删除命令。
- `checksums.json`：源文件字节哈希、规范化源对象哈希和计划哈希。

日志只含计数和哈希，失败只输出固定错误码，不输出姓名、学号、OpenID 或输入片段。材料不得添加到 Git、工单附件或聊天，不能放到同步公开目录。0600 是本机访问控制，不是加密；维护负责人应使用受控加密存储并约定访问者、保存期限、核验人和销毁方式。当前工具不是完整备份系统。

## 维护窗口与执行顺序

1. 单独确认环境、维护窗口、通知安排、保留管理员/班级清单、执行人及独立核验人。核实实际函数执行上限、存储路径和可用恢复材料。检查没有未完成旧维护任务。
2. 冻结旧协议写入并等待旧函数及上传排空。切换冻结不能借用旧 `cleaning` 标记冒充旧清理任务。迁移脚本中拒绝 V1 写的措施必须先生效，旧客户端返回“请更新小程序”。不能只隐藏旧页面或只切换客户端。
3. 冻结后重新获取完整旧工作区与 CAS revision；计算哈希、生成计划，并把恢复副本交给独立核验人。保留冻结前材料和最终冻结后材料以便比对。若 revision/epoch 变化，旧计划失效，重新导出核对；不静默重试覆盖。
4. 建立 V2 私有结构及 service_role-only RPC。通过 `xuedu_v2_cutover_prepare(p_plan)` 在事务中核对旧 revision/epoch、无旧维护任务、管理员和班级保留资料；新表必须为空。导入计划后仍处于 `workspace.maintenance = plan.id`。prepare 不删旧 workspace 或照片。不得用手写公共 SQL 绕过角色、唯一性或保留清单检查。
5. 独立导出全部 V2 资源，离线核对计数、ID、管理员原状态、学号、微信绑定、班级全部字段及空资源；再验证 service_role 外禁止私有表/RPC访问、旧协议被拒绝、保留管理员可被识别。不得先开放业务再检查。核对通过前不删除旧聚合数据。
6. 只有在上述核对完成且后续删除另获授权后，按固定旧轮次清单分批处理旧数据和照片。旧照片需在冻结后建立完整存储清单，包括未登记孤儿文件；`document.files` 不能证明桶中没有其他照片。本离线计划只标记旧 stage/epoch，并不声称该 epoch 是桶中全部旧照片范围。对其他历史轮次逐项核查、固定名单并单独确认。禁止把 `trial/` 作为新旧混合目录无限扫删，未知路径停止，失败保存进度续跑。
7. 导入和空表核对通过后，由受控服务端调用 `xuedu_v2_cutover_open(p_epoch, p_version, p_digest)` 进行事务内再次核对并解除维护。传计划的新轮次、维护工作区版本、计划 sha256。开放前若核对对象已变则拒绝。开放新版后复查旧 V1 写、旧清理及彻底重置启动接口均拒绝。实际部署任务应明确旧数据/照片清理与开放先后，不能在旧范围尚未固定时开放新写入。

`prepare/open` 接口仅供部署维护者使用，不暴露给小程序业务操作。它们的返回或离线 verified=true 不代表已经执行照片删除、已经通过真机验收或已经达到多年运行保障。

## 独立导出核对

核对输入格式：`{ target, workspace, resources }`。target 与计划相同；workspace 是 prepare 后仍维护中的完整对象；resources 必须包含协议 Resource 的**所有**键，每个键为对应表的完整 Entity 数组，即使为空也必须明确 `[]`。必须以受控服务端分页读完所有行再导出；不能用单页或客户端脱敏列表。bindings 含敏感身份，所以导出也必须保存在仓库外，0600。

```sh
node scripts/v2-cutover.mjs verify /受控目录/cutover-materials/retention-plan.json /受控目录/cutover-materials/legacy-recovery.json /受控目录/v2-export.json
```

验证会重建源清单，检查计划哈希、来源 revision/epoch、完整 workspace、三个保留资源的全部实体字段，其余业务资源必须明确为空。数据库内部 `cutover_manifest` 为最少维护元数据，不属于对外业务 Resource，不在上述导出内。服务端 open 会再次比对固定 manifest，不能仅凭命令行输出开放。

## 恢复界限与续跑

- 破坏性步骤前：保留原工作区、原照片和最终冻结快照。若新结构核对失败，保持维护并修复导入；受控维护者可以在独立确认 schema、旧协议及写入隔离后制定恢复安排，不能把换回代码当作已经恢复数据。
- 旧数据/照片删除开始后：记录任务 ID、固定旧范围、已完成批次和失败批次，优先修复后续跑。不能切回不认识 V2 的版本继续写入旧 workspace。代码回退不能恢复已删除照片；JSON 恢复副本也不含图片内容。
- 如需要照片可恢复能力，必须在另行授权的破坏性操作前准备和验证独立照片备份；当前交付未实现完整备份系统，不能承诺删除后的照片恢复。
- 原始副本不得在核对前删除。恢复材料的后续销毁需要维护者按批准保留期限执行；本工具不销毁材料。
